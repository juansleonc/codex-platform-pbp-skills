## Key Decisions

1. Keep this as a separate repo rather than embedding everything directly in `platform`.
   This keeps portable skills versioned independently and lets us install them through a Codex marketplace.

2. Treat `skills/` as the source of truth.
   The plugin copy under `plugins/pbp-platform-skills/skills/` is generated by `scripts/sync-plugin-skills.sh`.

3. Keep platform-specific behavior aligned with `platform/AGENTS.md`.
   Skills should operationalize those rules, not duplicate the full file.

4. Do not use Blacksmith/Testbox by default.
   Keep local-first validation unless a current user request explicitly asks for Blacksmith, Testbox, CI parity, or remote validation.

5. Port Claude/Superpower workflows selectively.
   Preserve useful procedures, remove product-specific assumptions, and replace unavailable tools with Codex-native equivalents.

## Skill Creation Plan

Create skills in batches. Each batch should be committed separately.

### Batch 1: Daily Platform Work

These should be created first because they cover most daily `platform` tasks.

1. `pbp-rails-change`
   Use for backend Rails changes involving controllers, services, policies, query objects, models, workers, Packwerk boundaries, or local validation.

2. `pbp-rspec-writer`
   Use for writing or repairing behavior-faithful RSpec specs with optimized fixtures, strong assertions, and meaningful non-happy paths.

3. `pbp-bug-reproduction`
   Use when a bug report, screenshot, bot finding, or review comment should be reproduced or falsified before editing.

4. `pbp-review-finding-validator`
   Use for evaluating bot findings, PR review comments, and suspected regressions; classify as confirmed bug, false positive, deferred debt, or needs more evidence.

### Batch 2: Contract and Safety Work

5. `pbp-graphql-change`
   Use for GraphQL query/mutation/schema changes, mobile compatibility, authorization, deferred query safety, and response contract checks.

6. `pbp-migration-safety`
   Use for database migrations, MySQL online DDL safety, `INSTANT` requirements, index planning, rollback checks, and production locking risk.

7. `pbp-e2e-evidence`
   Use for browser-driven validation, screenshots, console/network evidence, final verified states, and local URL workflows.

8. `pbp-payment-safety`
   Use for payment gateway, PCI, sandbox, trace ID, retry, idempotency, and external gateway consistency work.

### Batch 3: Domain Depth

9. `pbp-membership-change`
   Use for membership auto-renewal, cancellation, proration, payment retry, and membership business rules.

10. `pbp-multi-tenancy-check`
    Use for facility/org scoping, authorization leakage, cross-tenant queries, exports, and background jobs.

11. `pbp-performance-check`
    Use for N+1s, missing indexes, query plans, memory risks, cache strategy, and slow GraphQL/API paths.

12. `pbp-sidekiq-worker`
    Use for Sidekiq jobs, idempotency, retries, serialization safety, error handling, and queue behavior.

## Per-Skill Template

Every skill should follow this shape:

```text
skills/<skill-name>/
  SKILL.md
  references/      # only when detailed docs are needed
  scripts/         # only when deterministic automation is useful
```

`SKILL.md` requirements:

- YAML front matter with `name` and `description`.
- Description should be trigger-oriented and concise.
- Body should contain only essential workflow.
- Detailed domain rules should move to `references/`.
- Any referenced script or file must exist relative to the skill directory.

## Porting Workflow

Use `claude-skill-porting` when adapting Claude or Superpower skills.

Steps:

1. Read the source skill completely.
2. Extract the useful workflow and trigger.
3. Remove Claude/Superpower-specific tool assumptions.
4. Replace tools with Codex equivalents where possible.
5. Preserve stricter PBP safety rules.
6. Write a Codex-native `SKILL.md`.
7. Review with `codex-skill-review`.
8. Sync plugin copy.
9. Validate plugin.
10. Commit and push.

## Quality Bar

Before accepting a skill:

- The trigger is obvious from `description`.
- The skill is focused on one job.
- The body is shorter than necessary, not longer.
- It does not duplicate an existing better skill.
- It does not encourage unsafe default actions.
- It names validation commands or evidence expectations.
- It respects local-first validation for PBP.
- It does not assume Blacksmith/Testbox unless explicitly requested by the user.
